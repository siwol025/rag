## TO-001. 작업 저장과 큐의 구조: PostgreSQL + 별도 메시지 큐

**맥락**
- 기획서는 "FastAPI가 작업을 메시지 큐에 넣고 워커가 하나씩 가져간다"(PLAN.md:10, 27)고만 하고, DB 저장은 언급하지 않습니다. 대신 "AI 주변에 데이터베이스, redis, 메시지큐가 그대로 붙는다"(PLAN.md:22)고 합니다.
- 이벤트 수신 기능은 이미 FastAPI가 PostgreSQL `jobs` 테이블에 작업을 저장하고, `UNIQUE(channel_id, message_ts)`로 Slack 재전송 중복을 걸러냅니다(E2E로 확인).
- 큐를 붙일 때, 이 DB 저장을 유지할지가 문제였습니다.

**선택지**

| 안 | 흐름 | 장점 | 단점 |
|---|---|---|---|
| **A. DB + 큐** | FastAPI가 `jobs`에 INSERT → 큐에 `job_id`만 적재 → 워커가 `job_id`로 DB에서 읽음 | 중복 제거가 영구적. 작업 상태·결과·승인 대기를 DB에 기록할 수 있음. 이미 구현·검증한 코드를 그대로 씀. 큐 메시지가 작고 본문(개인정보)을 큐에 남기지 않음 | 한 요청에서 두 곳에 씀(이중 쓰기). DB 저장은 됐는데 큐 적재가 실패하면 워커가 그 작업을 모름 |
| B. 큐만 | FastAPI가 메시지 본문을 큐에 바로 적재. 중복은 큐의 작업 ID(`채널:ts`)로 막음 | 기획서 문장과 가장 가깝고 구조가 단순함 | 큐는 꺼내 가면 사라지는 통로라, 작업 결과가 큐에서 지워진 뒤에는 중복을 막지 못함. 진행 상태·승인 대기(수 분~수 일)를 남길 곳이 없어 결국 나중에 DB가 다시 필요함. 이미 만든 DB 코드를 걷어내야 함 |
| C. DB가 큐 역할 | `jobs`에 상태 컬럼을 두고 워커가 `FOR UPDATE SKIP LOCKED`로 직접 가져감 | 쓰기가 한 번(한 트랜잭션)이라 이중 쓰기 문제가 아예 없음. 새 인프라 없음 | 기획서의 "별도 메시지 큐" 구성과 다름. 재시도·격리(DLQ)·타임아웃을 직접 구현해야 함 |

**결정: A안**

**근거**
- 작업 상태를 남길 저장소는 어느 안이든 결국 필요합니다. LangGraph 체크포인트(F3), 재수정 이력(F8), 승인 대기(F9)가 모두 오래 보관해야 하는 상태입니다.
- DB 저장과 중복 제거는 이미 구현했고, 실제 Slack E2E까지 통과했습니다.
- 기획서의 구성 요소(DB, 메시지 큐)를 각자의 역할대로 씁니다. DB는 원본 기록, 큐는 "처리할 작업이 있다"는 알림입니다.

**감수한 비용과 대응**
- **이중 쓰기:** INSERT 성공 뒤 큐 적재가 실패할 수 있습니다. 대응 방향은 아래와 같고, 세부 구현은 큐 적재·워커 상세 계획에서 정합니다.
  - 큐 적재가 실패하면 FastAPI가 오류(5xx)로 응답해 n8n Retry On Fail이 다시 보내게 합니다.
  - 재시도 요청은 DB에서 `duplicate`로 걸리므로, **중복 요청이어도 아직 적재되지 않은 작업이면 다시 적재**해야 합니다. 따라서 큐 적재 자체가 `job_id` 기준으로 멱등해야 합니다(같은 `job_id`를 두 번 넣어도 한 번만 처리). 이 성질을 큐가 제공하는지가 TO-004의 판단 기준 중 하나입니다.
  - n8n 재시도는 약 20초(5초 간격, 최대 5회)가 한계입니다. 큐가 그보다 오래 내려가 있으면 DB에만 있고 큐에 없는 작업이 남습니다. 이를 다시 적재하는 장치(예: 미적재 작업을 주기적으로 다시 넣기)가 필요한지는 상세 계획에서 정합니다.

**다시 볼 조건**
- 큐 장애로 미적재 작업이 자주 생겨 보정 장치가 복잡해지면, C안(DB 큐)이나 트랜잭셔널 아웃박스 패턴을 검토합니다.

## TO-002. 워커 동시성: 워커당 1건, 워커 수로 확장

**맥락**
- 기획서는 워커가 "요청을 하나씩 가져간다"(PLAN.md:10)고만 합니다. 전역에서 1건씩인지, 워커마다 1건씩인지는 정하지 않았습니다.
- 작업 하나가 LLM 여러 번 호출과 테스트 실행으로 수 분 걸리고, 동시성이 높을수록 LLM 할당량(429)과 테스트 실행 자원을 서로 다툽니다.

**선택지**

| 안 | 장점 | 단점 |
|---|---|---|
| **워커당 1건, 워커 수로 확장** | 동시성을 "워커 프로세스 수" 하나로 조절함. 워커 안의 처리가 단순함(한 번에 한 작업) | 처리량을 늘리려면 프로세스를 더 띄워야 함 |
| 전역 직렬(시스템 전체 1건) | 가장 단순하고 비용 예측이 쉬움 | 작업이 몰리면 대기 시간이 길어짐. 100건 유입(PLAN.md:8)이면 수 시간 대기 |
| 워커당 N건 동시 | 자원 효율이 좋음 | 한 프로세스 안에서 LLM 429, 테스트 자원 경합을 다뤄야 함 |

**결정: 워커당 1건, 워커 수로 확장.** 개발 중에는 워커 1개로 시작합니다.

**근거:** 동시성을 조절하는 손잡이가 하나(워커 수)로 명확하고, 기획의 "하나씩"과도 맞습니다.

**감수한 비용:** 처리량이 워커 수에 비례하므로, 워커를 늘릴 때 LLM 할당량과 비용 상한(OQ-21)을 함께 봐야 합니다.

**다시 볼 조건**
- 같은 대상 저장소에 동시에 패치를 만들면 충돌할 수 있습니다. 코드 수정 단계(F5 이후)에서 "서비스·저장소별 직렬" 제약이 필요한지 다시 봅니다.

## TO-003. 배포 환경 전제: 지금은 로컬, 나중에 결정

**맥락**
- 배포 환경(OQ-19)은 큐 선택에 영향을 줍니다. GCP라면 관리형 Pub/Sub이 유력하고, 아니라면 자체 운영 큐가 맞습니다.

**결정(잠정):** 당분간 docker compose 로컬 개발만 하고, 코드는 특정 클라우드에 묶이지 않게 둡니다. 배포 환경은 기능이 어느 정도 갖춰진 뒤 정합니다.

**근거:** 지금 클라우드를 정하면 아직 필요 없는 계정, 권한, 비용 설정이 먼저 생깁니다.

**감수한 비용:** 나중에 GCP로 정하면 큐를 Pub/Sub으로 옮기는 선택지가 생길 수 있습니다. 그래서 큐를 쓰는 코드는 적재·소비 부분을 한곳에 모아 두는 편이 좋습니다.

**다시 볼 조건:** 배포 대상을 정할 때(OQ-19), F3에서 Gemini를 Vertex AI로 호출할지 Gemini API로 호출할지 정할 때.

## TO-004. 메시지 큐 구현체: Redis + arq

**맥락**
- TO-001(A안)에 따라 큐에는 `job_id`만 들어갑니다.
- 판단 기준(중요한 순서):
  1. **유실 없음:** 워커가 처리 중에 죽어도 작업이 다시 처리되는가(at-least-once).
  2. **멱등 적재:** 같은 `job_id`를 다시 넣어도 한 번만 처리되는가(TO-001의 이중 쓰기 대응).
  3. **재시도·격리:** 반복 실패 작업을 따로 빼 둘 수 있는가(DLQ).
  4. **장시간 작업:** 수 분짜리 작업을 타임아웃 없이 처리할 수 있는가.
  5. **운영 부담:** 새 인프라가 늘어나는가. Redis는 F3 캐시용으로 어차피 들어올 예정입니다(PLAN.md:22, 53).
- 규모는 "100건이 몰려도"(PLAN.md:8) 수준이라 처리 속도는 기준에서 뺐습니다.

**후보 비교** (출처: external-api-specs.md 8.4)

| 후보 | 유실 없음 | 멱등 적재 | 재시도·DLQ | 장시간 작업 | 운영 부담 | 정리 |
|---|---|---|---|---|---|---|
| **Redis + arq** | 워커가 죽으면 나중에 다시 실행(작업이 두 번 실행될 수 있음) | 같은 `_job_id`는 실행이 끝나기 전까지 다시 넣을 수 없음 | `max_tries` 기본 5. DLQ 미확인 *(결정 당시 조사. 이후 소스로 확인: DLQ 없음, 우리 설정 `max_tries=4`)* | `job_timeout` 기본 **300초** → 늘려야 함 | 낮음(Redis 재사용) | 직접 짤 코드가 가장 적음. asyncio 전용 |
| Redis Streams 직접 구현 | consumer group + `XACK`. ack 전까지 PEL에 남고 `XAUTOCLAIM`으로 회수 | 내장 없음 → 직접 구현 | DLQ 내장 없음 → 전달 횟수를 보고 직접 이동 | 직접 관리 | 낮음(Redis 재사용) | 동작을 완전히 통제하고 원리를 깊이 다루지만, 재시도·DLQ·멱등을 모두 직접 만듦 |
| Google Cloud Pub/Sub | ack 기반. exactly-once는 pull 구독·같은 리전에서만 | 발행자 재시도 시 중복 가능 | dead-letter topic, 최대 전달 5~100회 | ack 연장 상한 600초 | 관리형이지만 GCP 프로젝트·권한·로컬 에뮬레이터 필요 | TO-003(로컬 우선)과 맞지 않음 |
| RabbitMQ | 수동 ack, quorum queue | 내장 없음 | DLX, `delivery-limit` 기본 20 | 가능 | **높음**(새 인프라) | 기능은 충분하지만 이 규모에 비해 무거움 |
| Celery | 기본은 실행 직전 ack. `acks_late` + `task_reject_on_worker_lost` 필요 | 내장 없음 | 재시도 설정 풍부, Redis 브로커 DLQ 미확인 | 가능 | 중간 | 설정 함정이 많고 이 규모에 비해 큼 |
| RQ | 미확인 | 미확인 | 실패 작업 보관(`failure_ttl`) | `job_timeout` 기본값 미확인 | 낮음 | `fork()` 필요. 조사가 덜 됨 |

**결정: Redis + arq.** 우선 가장 쉬운 구현으로 시작하고, 서비스 운영 중 문제가 생기면 교체합니다.

**근거**
- **구현 난이도가 가장 낮습니다.** 판단 기준 1~4에 필요한 동작이 대부분 라이브러리에 들어 있습니다.
  - 유실 없음: 워커가 죽으면 작업을 나중에 다시 실행합니다.
  - 멱등 적재: 같은 `_job_id`를 실행이 끝나기 전까지 다시 받지 않습니다. `job_id`를 그대로 `_job_id`로 쓰면 TO-001의 "중복 요청 시 다시 적재"를 안전하게 할 수 있습니다.
  - 재시도: `max_tries`(기본 5). 우리 설정은 4(처리 3번 + 실패 기록용 1번, 감수한 비용 참고).
  - 장시간 작업: `job_timeout`을 설정으로 늘립니다.
- **새 인프라가 Redis 하나뿐이고, Redis는 F3 캐시에 재사용합니다**(PLAN.md:22, 53).
- Redis Streams 직접 구현은 같은 기능을 모두 손으로 만들고 테스트해야 해서, 지금 단계에서는 얻는 것보다 드는 비용이 큽니다.

**감수한 비용**
- **두 번 실행될 수 있습니다.** arq는 워커가 죽으면 작업을 다시 실행하는 방식(pessimistic execution)이라, 같은 작업이 두 번 돌 수 있습니다. 그래서 워커의 각 단계는 다시 실행돼도 안전하게(멱등하게) 만들어야 합니다. 예를 들어 LangGraph 체크포인트로 끝난 단계를 건너뛰고, Slack 게시 전에 이미 게시했는지 확인합니다.
- **DLQ가 없습니다**(arq 0.28.0 소스로 확인, 2026-11-13). 재시도를 다 쓴 작업은 `jobs.status='failed'`, `error='max_tries_exceeded'`로 DB에 격리합니다.
- **일반 예외와 `job_timeout` 초과는 재시도 없이 바로 실패합니다**(arq 0.28.0 소스로 확인). arq는 `Retry` 예외만 재시도하고, 이때 작업 함수는 DB에 아무것도 남기지 못해 작업이 `running`에 멈출 수 있습니다. 그래서 워커는 모든 예외를 `Retry`로 바꾸고, arq보다 30초 짧은 자체 타임아웃(600초)을 두며, arq `max_tries`를 우리 상한보다 1 크게 잡아 마지막 실행이 `failed`를 기록하게 했습니다(F2 계획 3.5).
- **기본 `job_timeout`이 300초입니다.** 설정으로 630초(자체 타임아웃 600초 + 여유 30초)로 늘렸습니다. 대가로 SIGKILL 뒤 재처리까지 최대 640초가 걸립니다.
- **워커 재시작도 시도 횟수를 씁니다.** SIGTERM으로 실행 중 작업이 취소돼도 arq가 시도 번호를 올립니다. 수 분짜리 작업이 도는 동안 워커가 여러 번 재시작되면 처리 실패가 없었어도 `failed`가 될 수 있어, F3에서 다시 봅니다.
- **결과 보관(`keep_result`)을 0으로 끕니다.** arq의 `_job_id` 중복 방지는 대기·실행 중과 결과 보관 기간에만 유효해 영구적이지 않습니다. 결과는 `jobs`가 원본이므로 arq 결과는 쓰지 않고, 끝난 작업을 다시 처리하지 않는 판단은 `jobs.status`가 맡습니다(F2 계획 3.2).
- **워커가 asyncio 기반입니다.** 워커 안에서 쓰는 DB·LLM 호출도 비동기 방식에 맞춰야 합니다. FastAPI 쪽 F1 코드는 동기(psycopg 동기)라 그대로 둡니다.
- **릴리스가 드뭅니다.** 조사 시점 최신은 0.28.0(2026-04-16)입니다. 유지보수가 멈추면 교체 사유가 됩니다.

**교체를 쉽게 하기 위한 약속**
- 큐 적재(FastAPI 쪽)와 소비(워커 쪽) 코드는 각각 한 모듈에 모으고, 나머지 코드는 arq를 직접 부르지 않습니다(TO-003과 같은 이유).
- 큐 메시지에는 `job_id`만 넣습니다(TO-001). 작업 내용과 상태는 PostgreSQL이 원본이라, 큐를 바꿔도 데이터는 옮기지 않아도 됩니다.

**다시 볼 조건(교체 검토 신호)**
- 재시도를 다 쓴 작업을 따로 격리·재처리하는 요구(DLQ)가 커져서, 직접 만든 보정 코드가 복잡해질 때 → Redis Streams 직접 구현 또는 RabbitMQ
- 배포 환경을 GCP로 정했을 때(TO-003, OQ-19) → Pub/Sub
- 큐가 오래 내려가 미적재 작업이 자주 생길 때(TO-001) → C안(DB 큐)이나 아웃박스 패턴
- arq 유지보수가 멈추거나, 쓰는 Python·Redis 버전을 지원하지 않게 될 때

## TO-005. DB 스키마 관리 방식: `schema.sql`을 API 시작 때 적용(마이그레이션 도구 없음) 유지

**맥락**
- F1에서 테이블 1개 규모라 ORM·마이그레이션 도구 없이 `schema.sql`(`CREATE TABLE IF NOT EXISTS`)을 API 시작 때마다 적용하기로 했습니다(F1 계획 3.5).
- F2에서 상태 컬럼을 추가하며 같은 파일에 `ALTER TABLE jobs ADD COLUMN IF NOT EXISTS …`를 이어 썼습니다.
- F2 리뷰에서 확인된 사실(일회용 PostgreSQL로 재현): `ALTER TABLE`은 **바꿀 컬럼이 없어도** 테이블에 가장 강한 잠금(ACCESS EXCLUSIVE)을 먼저 잡습니다. 그래서 다른 세션이 `jobs`에 트랜잭션을 열어 두면(읽기만 해도) API 시작이 멈추고, 그 뒤의 다른 작업도 줄을 섭니다. `CREATE TABLE IF NOT EXISTS`만 있을 때는 생기지 않던 일입니다.

**선택지**

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 그대로 두고 주의만 기록** | 코드 변경 없이 "jobs에 트랜잭션을 열어 둔 채 API를 재시작하지 말 것"을 문서에 적음 | 변경 없음 | 사람이 주의해야 함 |
| B. 잠금 대기 시간 제한 | 스키마 적용 때만 `lock_timeout`을 걸어 멈추는 대신 빨리 실패 | 멈추지 않고 원인이 로그에 남음 | 코드·테스트 추가 |
| C. 컬럼이 없을 때만 ALTER | 존재 여부를 먼저 조회 | 잠금 문제 자체가 없어짐 | SQL이 복잡해짐 |
| D. 마이그레이션 도구 | Alembic 등으로 "아직 적용 안 된 변경만 한 번" | 근본 해결 | 지금 규모에 과함 |

**결정: A안** (2026-11-15, F2 리뷰 지적 #2)

**근거**
- 이 문제는 **사람이 psql 등으로 `jobs`에 트랜잭션을 열어 둔 채** API를 재시작할 때만 생깁니다. 앱의 트랜잭션은 모두 몇 ms 안에 끝나고, 워커는 처리하는 동안 트랜잭션을 열지 않으므로(F2 계획 3.4) 자동 운영에서는 생기지 않습니다.
- 생겨도 psql에서 `COMMIT`/`ROLLBACK` 한 번으로 풀립니다.

**감수한 비용:** 수동 점검(F2 계획 M4처럼 행 잠금을 잡아 두는 절차) 중에는 API를 재시작하지 않도록 사람이 주의해야 합니다. 주의 문구는 F2 계획 3.8과 M4에 있습니다.
- **F3 추가(2026-11-16, F3 계획 리뷰):** F3 첫 기동 때 LangGraph 체크포인터 `setup()`이 실행하는 `CREATE INDEX CONCURRENTLY`는 `jobs`뿐 아니라 **DB 전체의 오래 열린 트랜잭션**이 끝나기를 기다릴 수 있습니다(첫 적용 때만). F3를 처음 띄울 때는 psql 등으로 열어 둔 트랜잭션이 없는지 확인합니다. F3도 `schema.sql`에 `ALTER`를 더하므로, 스키마 변경이 늘어나는 F4에서 이 결정(마이그레이션 도구 여부)을 다시 점검합니다.
- **F4 점검(2026-11-18, F4 결정):** F4에서 늘어나는 스키마를 보고 다시 점검한 결과입니다.
  - **결정:** A안(지금 방식 그대로, 주의만 기록)을 유지합니다. `schema.sql`에는 `IF NOT EXISTS` 형태로 추가만 합니다.
  - **F4에서 늘어나는 스키마:** `CREATE EXTENSION vector`, 문서·조각 표, 인덱스, `jobs` 답변 컬럼. 모두 추가형입니다.
  - **색인 컨테이너(TO-014)와 겹칠 때:** `CREATE INDEX IF NOT EXISTS`는 인덱스가 이미 있어도 그 표에 SHARE 잠금을 먼저 잡습니다. 그래서 색인 쓰기 트랜잭션이 열려 있으면 API 시작이 기다립니다(일회용 컨테이너로 확인, `docs/researchs/rag-document-search.md` 2.4). 대응은 두 가지입니다. 색인은 문서 하나씩 짧게 커밋하고, 임베딩 호출은 트랜잭션 밖에서 끝냅니다.
  - **도구를 도입할 시점:** 되돌리기 어려운 변경이 처음 생길 때입니다. 가장 유력한 경우는 벡터 차원 변경(768 → 1,536, TO-011)입니다. 그때 D안(마이그레이션 도구)을 도입하되, 번호 붙은 SQL 파일과 적용 기록 표를 직접 만드는 방식으로 합니다. Alembic은 SQLAlchemy 기반이라 psycopg를 직접 쓰는 지금 구조와 맞지 않습니다.

**다시 볼 조건**
- 스키마 변경이 F3, F4에서 계속 늘어날 때 → D(마이그레이션 도구)
- `jobs`에 오래 열린 트랜잭션을 만드는 코드가 생길 때(처리 전체를 한 트랜잭션으로 감싸기, 트랜잭션 안의 긴 집계 쿼리 등) → 자동 운영에서도 생길 수 있으므로 B·C·D 검토
- 이름·타입 변경처럼 되돌릴 수 없는 스키마 변경이 처음 생길 때 → D(F1 계획 3.5의 기존 조건)

## TO-006. 분류 체계(서비스·카테고리) 관리: 지금은 수동 목록 파일, 실서비스에서 서비스 카탈로그 연동으로

**맥락**
- F3의 분류 노드는 요청 유형과 함께 **서비스**(예: `payment-api`)와 **카테고리**(예: `server-error`)를 뽑습니다.
- 이 값은 F4에서 문서 검색 범위를 먼저 좁히는 필터로 씁니다(PLAN.md:53). 필터는 글자가 정확히 같아야 걸리므로, 분류 결과와 문서 꼬리표의 값이 **항상 같은 표기**여야 합니다.

**선택지**

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 수동 목록 파일** | 저장소에 목록 파일을 두고 LLM은 그 안에서만 고름(구조화 출력의 선택지 제한, 없으면 `unknown`) | 값이 항상 일정해 필터가 확실히 걸림. 문서 꼬리표도 같은 목록 사용 | 새 서비스가 생기면 사람이 목록에 추가 |
| B. LLM 자유 추출 | 목록 없이 LLM이 이름을 붙임 | 관리 없음 | 같은 서비스가 `결제`, `payment-api`, `Payment API`처럼 제각각 → 필터가 빗나감 |
| C. 서비스 카탈로그 연동 | 회사의 서비스 목록 시스템(예: Backstage)에서 자동으로 가져옴 | 목록이 자동으로 최신 | 연동할 카탈로그가 있어야 함 |

**결정: 지금은 A, 실서비스에서는 C로 옮겨 감** (2026-11-16)

**근거**
- 개발 단계라 실제 서비스 목록도 카탈로그 시스템도 없습니다. C는 연동 대상이 없고, B는 F4 필터 문제가 처음부터 생깁니다.
- 초기 목록은 샘플로 시작하고, 실제 대상 저장소를 정할 때(OQ-02) 바꿉니다.

**C로 옮기기 쉽게 하는 약속**
- **목록을 읽는 곳은 한 함수로 모읍니다.** 분류 노드와 F4 문서 꼬리표가 같은 함수로 목록을 가져오게 해, C로 바꿀 때 그 함수 안의 "파일 읽기"만 "카탈로그 조회"로 바꿉니다(TO-004의 큐 모듈과 같은 원리).
- **꼬리표 값은 바뀌지 않는 ID로 씁니다.** `payment-api`처럼 영문 소문자 ID를 쓰고 표시용 이름("결제 API")은 따로 둡니다. ID가 바뀌면 이미 꼬리표를 붙인 문서를 모두 다시 붙여야 합니다. C로 옮길 때는 카탈로그의 서비스 ID와 맞춥니다.

**감수한 비용:** 새 서비스가 생겨도 목록에 추가하기 전까지는 `unknown`으로 분류되고, 그동안 검색 필터를 쓸 수 없습니다.

**다시 볼 조건**
- 실서비스(실제 팀 워크스페이스, 실제 대상 저장소)로 옮길 때 → C 검토
- 목록 누락으로 `unknown`이 자주 나올 때
- 운영 단계에서 비개발자가 목록을 관리해야 할 때 → **웹 관리 화면** 검토(사용자 아이디어, 2026-11-16). 목록을 DB 표에 두고 로더 함수가 그 표를 읽게 바꾸면, 분류 노드와 F4 코드는 그대로이고 작업마다 다시 읽으므로 재배포 없이 반영됨. 화면에서도 ID는 추가와 표시 이름 변경만 허용하고, 삭제 대신 "사용 안 함" 표시를 둠(이미 저장된 작업·문서 꼬리표 보호)

## TO-008. LLM 호출 경로: 테스트 단계는 Gemini API 무료 요금제(결제 계정 미연결)

- TO-007에서 Vertex AI(global)로 정한 직후, 사용자가 **"테스트 단계에서는 무료 토큰만 쓰고, 그 이상 사용해 결제가 되는 것을 막고 싶다"**는 요구를 추가했습니다(2026-11-16).

  - **Vertex AI는 무료 체험 크레딧으로 쓸 수 없습니다.** 2026-11-16 이후 무료 체험을 시작하거나 유료로 전환한 계정은 $300 크레딧을 Gemini platform(이전 Vertex AI) 비용에 쓸 수 없습니다([Google Cloud 무료 프로그램](https://docs.cloud.google.com/free/docs/free-cloud-features)). 지금 새로 만들면 Vertex 호출은 실제 결제 수단으로 청구됩니다.
  - **지출 상한(spend cap)은 0원을 보장하지 않습니다.** 사용을 자동으로 멈추지만 "즉시 적용되지 않고 초과분은 정상 청구"됩니다([Spend cap budgets](https://docs.cloud.google.com/billing/docs/how-to/budgets-spend-caps)). 일반 예산 알림은 알림만 보냅니다.
  - **Gemini API 무료 요금제는** `gemini-3.5-flash-lite`의 입력·출력이 무료입니다([Gemini API pricing](https://aistudio.google.com/docs/pricing)). 유료 등급으로 가려면 결제 계정을 직접 연결해야 하고, 한도를 넘으면 `429 RESOURCE_EXHAUSTED` 오류로 거절됩니다([Rate limits](https://aistudio.google.com/docs/rate-limits)).

**선택지**

| 안 | 결제 가능성 | 장점 | 단점 |
|---|---|---|---|
| **A. Gemini API 무료 요금제**(AI Studio API 키, 결제 계정 미연결) | **없음**(청구할 결제 계정 자체가 없음) | 요구와 정확히 맞음. GCP 프로젝트·gcloud·인증 파일이 필요 없어 준비가 가장 간단 | 보낸 내용이 Google 제품 개선에 쓰일 수 있음. 사용 한도가 낮아 `429`가 날 수 있음 |
| B. Vertex AI + 결제 계정 + 지출 상한(소액) | 있음(소액 초과 가능) | 기획(PLAN.md:20)과 같고 GCP 배포로 바로 이어짐 | 결제 수단 등록 필요, 0원 보장 안 됨 |

**결정: A안** (2026-11-16)

**근거**
- "결제가 절대 발생하지 않음"을 구조로 보장하는 방법은 결제 계정을 연결하지 않는 A뿐입니다. 한도를 거는 방식(B)은 집계 지연 때문에 과금이 새어 나갈 틈이 있습니다.
- A와 Vertex AI는 같은 `google-genai` SDK라, 나중에 인증과 설정만 바꿔 Vertex AI로 옮길 수 있습니다. 분류 노드 코드는 바뀌지 않습니다.
- 경량 모델과 역할 → 모델 ID 매핑 설정은 TO-007 그대로입니다.

**감수한 비용**

**지켜야 할 것**

## TO-009. LLM 호출 오류·속도 제어: 테스트 단계는 429 대처만, rate limiter는 유료 전환 때

**맥락**
- F3부터 Gemini API 무료 요금제(TO-008)를 호출합니다. 무료 요금제는 분당 요청 수(RPM)·분당 토큰 수(TPM)·일일 요청 수(RPD) 한도가 있고, 넘으면 `429 RESOURCE_EXHAUSTED`로 거절됩니다(과금 없음). 정확한 숫자는 AI Studio 화면에서만 확인할 수 있습니다.
- F3 계획 초안은 분당 한도 429를 일반 실패처럼 **시도 횟수(3회)를 쓰며** 60초 뒤 재시도했습니다. 리뷰에서 문제가 드러났습니다: 워커는 한 번에 1건을 처리하므로 429를 받은 작업을 미뤄 두고 곧바로 다음 작업을 가져가 또 429를 받습니다. 그래서 **분당 한도의 약 3배를 넘는 요청이 몰리면 실제 오류 없이도 `failed`가 대량으로 생깁니다**(예: 분당 10회, 50건 몰림 → 약 20건 실패). 기획의 "요청이 몰려도 큐에 쌓아 두고 처리"(PLAN.md:8-11)와 맞지 않습니다.

**선택지**

| 안 | 내용 | 판단 |
|---|---|---|
| A. 시도 횟수를 쓰며 재시도(초안) | 429 = 실패 1번, 60초 뒤 | 몰리면 실패 발생, 헛호출 많음 |
| **B. 그 자리에서 기다렸다 다시** | 분당 429면 시도 횟수를 쓰지 않고 같은 작업 안에서 60초 대기 후 재호출(최대 5번) | 워커당 1건 구조가 그대로 속도 조절 장치가 됨. 늦어질 뿐 실패 없음 |
| C. rate limiter(호출 전 제한) | Redis 공유 카운터로 분당 한도 전에 멈춤 | 429 자체를 막는 근본 해결이지만 정확한 한도 숫자와 Google의 집계 방식을 알아야 하고, 무료 요금제용으로 만들면 유료 전환 때 다시 짜야 함 |

**결정(테스트 단계, 2026-11-16)**
- **분당 한도 429: B.** 그 자리에서 60초 기다렸다 다시 부름(최대 5번, 300초로 처리 상한 600초 안). 5번 뒤에도 429면 일반 일시 오류로 보고 10초 뒤 재시도(시도 1번 사용).
- **일일 한도 429:** 기다려도 한국 시각 17시(태평양 자정)까지 풀리지 않으므로 바로 `failed('llm_quota_exhausted')`.
- **다시 해도 안 되는 오류(400·401·403·404):** 바로 `failed('llm_request_rejected')`. 잘못된 키·모델 ID는 재시도해도 같아 대기 작업마다 헛호출만 생기기 때문.
- **일시 오류(408·5xx·연결 오류·요청 시간 초과)와 출력이 목록 밖인 경우:** 10초 뒤 재시도(시도 3번).
- **rate limiter: 테스트 단계에서는 넣지 않음.** 유료(Vertex AI) 전환 때 그 할당량에 맞춰 Redis 공유 rate limiter를 도입(사용자 결정).

**근거**
- 테스트 단계는 워커 1개와 개발 워크스페이스 테스트 메시지뿐이라 몰릴 일이 드물고, 가끔 생기는 429는 B로 충분히 버팁니다.
- 무료 요금제와 유료 Vertex AI는 한도 체계가 달라, 지금 무료 숫자에 맞춘 rate limiter는 전환 때 다시 만들어야 합니다. 유료 단계에서는 호출이 곧 비용이고 한도 숫자도 콘솔에서 정확히 알 수 있어, 그때 만드는 것이 맞습니다.
- 재시도는 "시간이 지나면 나아질 오류"에만 의미가 있습니다. 그래서 오류를 기다리면 풀리는 것(분당 한도), 오래 기다려야 풀리는 것(일일 한도), 기다려도 안 풀리는 것(영구 오류)으로 나눠 다르게 처리합니다.

**감수한 비용**
- 몰리면 처리가 늦어집니다(분당 한도 속도로 줄을 섬).
- 429를 기다리는 도중 워커가 재시작되면 재시작 대기(60초) 뒤 취소되어 시도 1번을 씁니다.
- 같은 키를 다른 곳(AI Studio 화면 등)에서도 쓰면 우리 쪽 대기와 무관하게 429가 날 수 있습니다.

**다시 볼 조건**
- 유료(Vertex AI) 전환 때 → Redis 공유 rate limiter 도입(이때 TO-004의 "Redis·arq는 큐 모듈 두 곳에서만" 약속을 "arq는 두 곳, Redis의 다른 용도는 해당 모듈 하나"로 다듬음), 일일 한도 판별 로직 재검토
- 테스트 단계에서도 429 대기가 잦아 개발이 막힐 때

## TO-010. LLM 응답 캐시의 위치: F3(분류)에는 없음, F4·F5에서 의미 기반 답변 캐시

**맥락**
- 로드맵은 F3에서 "LLM 응답 캐시"를 처음 도입한다고 적었습니다.
- 사용자가 밝힌 캐시의 목적: **서로 다른 메시지라도 원하는 답이 같으면 토큰을 쓰지 않고 답하기.** 같은 작업 재실행이나 같은 메시지 재수신 같은 중복 호출 방지가 목적이 아님(이것은 체크포인트와 `jobs` 중복 제거가 이미 막음).
- "원하는 답이 같은지"는 답을 구하기 전엔 알 수 없으므로, 실제로는 **뜻이 비슷한 질문이면 답도 같다**고 보는 의미 기반 캐시(본문 임베딩 → 이전 질문 벡터와 유사도 비교 → 기준 이상이면 재사용)로 근사합니다.

**선택지와 판단**

| 안 | 판단 |
|---|---|
| F3 분류에 글자 일치 캐시 | 본문 해시만 비교해 싸지만, 글자까지 같은 본문은 드물고 아끼는 것이 가벼운 분류 호출이라 이득이 작음 |
| F3 분류에 의미 기반 캐시 | 비교에 임베딩 호출이 매번 필요. 분류 자체가 호출 1번이라 적중해도 본전이고, **캐시 미스면 임베딩 + 분류로 오히려 호출이 늘어남** |
| **F4·F5 답변에 의미 기반 캐시** | F4에서 검색용으로 질문을 어차피 임베딩하므로 비교 비용이 추가로 들지 않고, 적중하면 문서 검색 뒤의 고성능 모델 답변 생성(가장 비싼 부분)을 건너뜀 |

**결정** (2026-11-16): **F3에는 캐시를 넣지 않고, F4·F5에서 의미 기반 답변 캐시를 설계합니다.**

**F4·F5 설계 때의 원칙(미리 정해 둔 것)**
- F4 검색용 질문 임베딩을 캐시 비교에 재사용합니다.
- 문장이 비슷해도 답이 다를 수 있으므로(예: "결제 API 500 에러"와 "400 에러"), **F3 꼬리표(유형·서비스·카테고리)가 같고 유사도도 기준 이상일 때만** 재사용합니다.
- 질의응답형부터 적용하고, 오류 메시지의 작은 차이가 답을 바꾸는 코드 수정형은 신중하게 적용합니다.
- 답변은 검색된 문서와 대상 코드 상태에도 달려 있으므로, 문서 갱신 시 옛 답을 버리는 기준과 유사도 기준값을 그때 샘플로 정합니다.

**판단 기준(일반화):** 캐시는 "캐시를 확인하는 비용"이 "건너뛰는 작업의 비용"보다 충분히 작을 때만 이득입니다.

**다시 볼 조건**
- F4·F5 계획을 세울 때(설계 시작)
- 유료 전환 뒤 같은 본문의 반복 분류가 비용에서 의미 있는 비율이 될 때(글자 일치 분류 캐시 재검토)

**F4 계획 때 갱신 (2026-11-18): 언제 만들지는 조건 기반**

F4 결정 과정에서 유료 단가로 계산해 보고, **F4에서는 만들지 않기로** 했습니다. 아래 조건 중 하나가 먼저 오면 만듭니다. 자세한 근거는 `docs/researchs/rag-document-search.md` 7장에 있습니다.

| 질문 1건(질의응답) 유료 환산 | 분류 | 질문 임베딩 | 답변 | 합계 | 캐시 적중 시 |
|---|---|---|---|---|---|
| 답변 `gemini-3.5-flash-lite` | $0.00018 | $0.000006 | 약 $0.0016 | 약 $0.0018 | 약 $0.0002 |
| 답변 `gemini-3.8-flash`(2027 단가) | 같음 | 같음 | 약 $0.0065 | 약 $0.0067 | 같음 |

- 분류 토큰은 실측값입니다. 답변 토큰(입력 약 2,800, 출력 약 300)은 추정입니다.

**만드는 조건(먼저 오는 것)**
1. 유료로 전환할 때(TO-008)
2. 답변 모델을 상위 모델로 올릴 때(TO-016)
3. `llm_usage`에서 답변 호출 비용이 눈에 띄게 커질 때

**그때 지킬 설계(F4 결정 과정에서 더한 것 포함)**
- 검색용 질문 임베딩을 재사용합니다. 저장소는 pgvector 표 하나입니다(TO-012).
- 꼬리표(유형·서비스·카테고리)가 같고, `embedding_model`과 `answer_model`도 같을 때만 재사용합니다.
- **근거 문서 해시 확인:** 조회할 때 후보 답이 인용한 문서의 현재 `content_hash`가 저장된 값과 모두 같아야 적중으로 봅니다.
- **새 문서 누락 대응(새로 찾음):** 근거 해시만 보면 "새 문서가 추가된 경우"를 못 잡습니다. 예를 들어 3월 장애 답을 캐시한 뒤 11월 회고가 추가되어도 옛 답이 나갑니다. 그래서 같은 꼬리표의 문서가 추가되거나 수정되면 그 꼬리표의 캐시를 버리거나, 보존 기간(TTL)을 둡니다.

- 유사도 기준값은 live로 정합니다. "같은 뜻의 질문 쌍"과 "비슷하지만 답이 다른 쌍"(예: 결제 5xx와 4xx)의 유사도를 재서 그 사이에 둡니다.

## TO-012. Vector DB: pgvector(지금 PostgreSQL 재사용), 이미지 교체와 개발 볼륨 재생성

- PostgreSQL이 18.6에서 18.7로 부 버전만 올라갑니다.
- 확장은 슈퍼유저가 만들어야 합니다. compose의 `POSTGRES_USER`는 공식 이미지에서 슈퍼유저입니다.

**다시 볼 조건**
- 조각 수가 수만 개를 넘거나 검색 시간이 눈에 띌 때 → HNSW + `hnsw.iterative_scan`, 또는 서비스별 부분 인덱스

- 지워서는 안 되는 데이터가 있는 DB에서 이미지를 바꿀 때 → 볼륨을 다시 만들지 말고 `REINDEX DATABASE` + `ALTER DATABASE … REFRESH COLLATION VERSION`

## TO-014. 색인 실행 방식: 주기 확인(5분) + CLI, 색인 전용 컨테이너

**맥락**
- 사용자 요구: 문서가 업데이트되면 알아서 임베딩되어야 합니다(사람이 명령을 기억하는 방식은 부족).
- 색인은 해시로 바뀐 조각만 임베딩합니다. 그래서 바뀐 게 없으면 몇 번을 돌려도 임베딩 호출이 0회입니다.

**선택지**

| 안 | 반영 속도 | 임베딩 호출 | 판단 |
|---|---|---|---|
| A. 수동 CLI만 | 사람이 돌릴 때 | 바뀐 만큼 | 잊으면 옛 내용으로 답함 |
| B. 주기 확인, 기존 `worker` 안에서 | 최대 5분 | 바뀐 만큼. 간격 안에 여러 번 저장하면 마지막 것만 | 색인이 Slack 작업과 워커 자리 1개(TO-002)를 나눠 씀 |
| **B′. 주기 확인, 색인 전용 컨테이너** | 최대 5분 | 같음 | Slack 작업 워커와 완전히 분리 |
| C. 파일 감시 | 몇 초 | **저장할 때마다**(중간 저장까지) | 꺼져 있던 동안의 변경을 놓쳐 시작할 때 전체 비교가 필요함. Docker Desktop의 파일 변경 알림 전달은 미확인. 개발 단계에서만 쓰임 |
| D. GitHub push 웹훅 | push 직후 | 바뀐 만큼 | 운영 소스가 미정. 유실 대비 안전망, 터널, 서명 검증, 웹훅 등록이 필요 |

**결정** (2026-11-18): **B′. 5분 주기 확인 + CLI, `indexer` 전용 컨테이너**(같은 이미지, 실행 명령만 다름). 기존 `worker`는 Slack 작업만 처리합니다.

**근거**
- 주기 확인의 비용은 로컬에서 파일을 읽고 해시를 비교하는 것뿐입니다. 임베딩은 바뀐 만큼만 부르므로 파일 감시보다 같거나 적습니다.
- 매번 전체를 비교하므로 삭제를 포함한 모든 변경을 잡습니다. 어느 회차가 실패해도 다음 회차가 이어서 처리합니다.
- 전용 컨테이너로 두면 색인(429 대기 포함)이 Slack 작업의 처리 자리를 쓰지 않습니다.
- 웹훅은 "가장 빠른 신호"이지 "확실한 신호"가 아닙니다. 그래서 운영에서도 주기적으로 맞추는 안전망이 필요합니다. B′는 그 안전망 층을 먼저 만드는 셈입니다.

**함께 지킬 것(계획에 반영)**
- 색인은 429가 나면 기다리지 않고 멈춥니다. 다음 회차가 해시로 이어서 처리합니다.
- 색인은 한 번에 하나만 돕니다(DB advisory lock). CLI와 주기 작업이 겹치는 경우를 막기 위해서입니다.
- 임베딩 호출은 트랜잭션 밖에서 끝내고, 문서 하나씩 짧게 커밋합니다(TO-005).
- 바뀐 게 있을 때만 로그를 남깁니다. 시작할 때 1회 실행합니다.
- 문서 폴더는 `indexer`에 읽기 전용으로 연결합니다(bind mount).
- 첫 전체 색인은 분당 토큰 한도(TPM 30K, TO-011) 때문에 여러 회차에 걸칠 수 있습니다.

**감수한 비용**
- 반영이 최대 5분 늦습니다(급하면 CLI).
- 컨테이너가 1개 늘어납니다.
- 전체를 훑는 비용이 문서 수에 비례합니다.
- 일일 한도에 걸리면 문서 사이에 "일부만 반영된" 상태가 한동안 남습니다. 문서 하나 안에서는 트랜잭션이라 섞이지 않습니다. 처리할 변경이 남아 있는 동안 회차마다 거절 호출이 1번씩 생깁니다.
- 사람이 확인하는 단계가 없습니다. 그래서 TO-013의 샘플 전용 폴더 규칙을 둡니다.

**다시 볼 조건**
- 문서가 수천 건을 넘어 한 바퀴가 무거워질 때 → 전체 훑기 대신 수정 시각이나 커서로 바뀐 것만 찾기
- 운영 문서 소스를 정할 때 → 그 소스의 웹훅(빠름) + 커서 기반 주기 맞추기(안전망, 간격을 늘림)

## TO-015. 검색 범위: 꼬리표 단계별 풀기(서비스+카테고리 → 서비스), F4는 질의응답만 검색

**맥락**
- F3 분류의 서비스·카테고리로 먼저 좁힙니다(TO-006).
- 카테고리는 원인을 판단해야 해서 질문 시점에 틀리기 쉽습니다.
- `code_fix` 경로는 F5 전까지 빈 노드입니다.

**선택지**

| 안 | 판단 |
|---|---|
| 고정 필터(서비스+카테고리) | 카테고리가 틀리면 정답을 놓침 |
| **단계별 풀기 ①서비스+카테고리 → ②서비스** | 평소에는 좁게 찾고, 놓칠 때만 넓힘 |
| 단계별 풀기 + ③전체 | 서비스 오분류에도 찾지만, 다른 서비스 문서를 근거로 답할 위험 |
| 서비스만 | 카테고리로 좁히기(기획)를 쓰지 않음 |
| `code_fix`도 검색 | F5 전까지 결과를 쓰는 곳이 없음. F5는 다른 질의(예외 이름 등)가 필요할 수 있음 |

**결정** (2026-11-18)
- **① 서비스+카테고리 → (기준을 넘는 결과가 k개 미만이면) ② 서비스만. ③ 전체는 두지 않습니다.**
- 값이 `unknown`인 조건은 걸지 않습니다.
  - 그래서 질문에 서비스가 없으면(`unknown` / 카테고리) ①은 카테고리만, ②는 조건 없음(전체)이 됩니다. 이 경우에는 "다른 서비스"라는 개념이 없고 풀리는 것은 카테고리뿐이라, ③(다른 서비스로 넓히기)과 다르게 봅니다(2026-11-19 계획 검토에서 승인).
- **F4는 `question`만 검색합니다**(`classify → retrieve → answer`). `code_fix`는 지금처럼 빈 노드로 둡니다.

**근거**
- 질문 임베딩은 1번이고, 늘어나는 것은 DB 조회(최대 2번)뿐입니다.
- live에서 서비스 분류는 12건 중 12건 정답이었습니다.
- 다른 서비스 문서를 인용하면 답이 헷갈립니다(함정 문서, TO-013).
- `code_fix` 검색은 쓰이지 않는 임베딩 호출입니다. `retrieve`를 노드로 만들어 두면, F5에서는 간선 하나만 더하면 됩니다. Researcher는 두 경로 공통 검색을 권했지만, 사용자가 질의응답만으로 결정했습니다.

**감수한 비용**
- 서비스가 틀리면 "근거 없음"이 됩니다.
- F5에서 `code_fix` 검색의 질의를 따로 설계해야 합니다.

**다시 볼 조건**
- 서비스 오분류로 정답을 놓치는 사례가 보일 때 → ③ 추가
- 서비스를 모르는 질문에서 관련 없는 다른 카테고리 문서가 근거로 나올 때 → 그 경우는 ①(카테고리만)에서 멈춤
- F5 계획 때 → `code_fix` 검색 여부와 질의 방식

## TO-016. 답변 생성: 경량 모델 재사용, 근거 없으면 호출 없이 "찾지 못함", 인용은 넣은 조각 ID로만

**맥락**
- RAG에서 가장 위험한 실패는 문서에 없는 내용을 지어내는 것(환각)입니다.
- 무료 요금제 한도 안에서 답해야 합니다.

**선택지**

| 안 | 판단 |
|---|---|
| **답변 `gemini-3.5-flash-lite`** | 한도(RPM 15·RPD 500)와 품질을 이미 확인함. 새 설정 키가 필요 없음 |
| `gemini-3.8-flash` / `gemini-4-hydrogen` | 무료지만 한도가 미확인. 새 설정 키가 필요하고, 사고 토큰이 나올 수 있음 |
| 항상 모델을 부르고 "모른다"는 판단을 맡김 | 관련 없는 문서를 넣으면 억지로 엮어 답할 위험. 호출도 늘어남 |
| **기준 미달이면 호출 없이 고정 문구** | 호출을 아끼고, 관련 없는 문서를 아예 넣지 않음 |

**결정** (2026-11-18)
- **모델:** `gemini-3.5-flash-lite`(`LLM_LIGHT_MODEL` 재사용)
- **근거가 없을 때:** 최고 유사도가 기준 미만이면 모델을 부르지 않고 "관련 문서를 찾지 못했습니다"(`found=false`)로 답합니다.
- **답변 형식:** 그 밖에는 구조화 출력 `{found, answer, citations}`으로 받습니다.
  - `citations`는 **이번에 넣은 조각 ID로만 고를 수 있게(enum)** 제한하고, 코드로 다시 검증합니다. 위반하면 F3 규칙대로 재시도합니다.
- **프롬프트 구성:** 지시문은 `system_instruction`, 질문은 `<question>`, 문서는 `<document>`에만 넣고, 태그 안은 데이터로 취급합니다(F3 3.11 확장).
- **저장:** 답변은 작업이 완료될 때 `jobs`에 함께 저장합니다(F3 방식).

**근거**
- 기획의 "간단한 건 가벼운 모델"(PLAN.md:53)과 맞습니다.
- 답변 품질은 모델보다 검색이 맞는 문서를 가져오는지에 더 크게 좌우됩니다.
- enum을 쓰면 "인용이 실제로 준 문서인가"를 코드가 확인할 수 있습니다.

**감수한 비용**
- 분류와 답변이 같은 한도(RPD 500)를 나눠 씁니다. 질의응답만 들어오면 하루 약 250건입니다.
- 유사도 기준값은 공식 출발점이 없어 live로 재야 합니다.
- enum은 답변 **문장**이 문서와 맞는지까지는 보장하지 못합니다. 그래서 live 테스트로 확인합니다.
- 자유 문장인 `answer`에 문서 속 주입 내용(링크 등)이 옮겨질 수 있습니다. 이는 F9에서 Slack 표시 규칙으로 막습니다.

**다시 볼 조건**
- live 답변 품질이 부족할 때 → `gemini-3.8-flash`(먼저 AI Studio에서 무료 한도를 확인하고, 그때 역할 설정 키를 추가)
- 유료로 전환할 때(TO-008, TO-010 캐시 조건과 함께)
