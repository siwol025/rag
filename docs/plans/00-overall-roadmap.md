> 작성일 2026-11-11 · 입력: `PLAN.md`, `docs/researchs/plan-architecture.md`(OQ 번호는 9장), `docs/researchs/external-api-specs.md` · 기능 단위와 순서만 다루며, 설계·스키마·라이브러리 선택은 기능별 상세 계획(`docs/plans/NN-*.md`)에서 다룹니다.

## 1. 목적과 개발 원칙

**목적**: 기획서의 전체 흐름(PLAN.md:56-66)을 기능 단위 F1~F9로 나누고, 상세 계획을 쓸 순서를 정합니다.
- **데이터 흐름 순서**: 이벤트가 들어오는 Slack 수신(앞단)부터 Slack 회신(끝단)까지 흐름대로 만듭니다.
- **기능 1개 = 상세 계획 1편**: 각 기능은 끝에서 검증할 수 있는 결과를 하나 남깁니다.
- **작업 기록으로 검증**: F2~F8은 작업 기록(상태, 단계별 산출물)으로 확인하고, Slack 회신은 흐름 끝인 F9에서 만듭니다. 임시 대체(stub)는 다음 단계가 없어 검증이 막힐 때만 씁니다.
- **OQ는 상세 계획 전에**: 각 기능에 걸린 미결정 사항(OQ)을 사용자가 정한 뒤 그 기능의 상세 계획을 씁니다.

## 3. 단계별 요약

### F1. 이벤트 수신 (Slack → n8n → FastAPI)
- **목표**: 대상 채널의 메시지가 사람 개입 없이 FastAPI에 작업으로 접수됩니다(PLAN.md:3-6).
- **입력 → 출력**: Slack 채널 메시지 → 작업 기록 1건 + `202 {job_id}`
- **포함 범위**
  - Slack 앱 설정과 n8n Slack Trigger 워크플로(대상 채널, 서명 검증, 자기 봇 메시지 차단)
  - FastAPI `POST /jobs`: n8n 호출 인증, 입력 검증, 즉시 202 응답(AI 작업은 하지 않음)
  - 작업 기록 저장과 중복 수신 처리(Slack 재시도로 같은 메시지가 다시 와도 1건)
- **완료 기준**: 채널에 메시지를 쓰면 작업 기록이 생기고 202가 반환된다. 같은 요청을 다시 보내면 새 작업이 생기지 않는다.
- **먼저 정할 것**: OQ-05(입력 형식, 봇 알림도 요청으로 받을지), OQ-06(트리거 조건), OQ-07(n8n 역할과 호스팅), OQ-24(Slack 앱 배포 형태)
- 가정: 공통 기반(프로젝트 골격, 로컬 실행 환경, 설정)은 별도 단계 없이 F1에서 필요한 만큼만 만듭니다. DB, 큐, Redis, Vector DB, 실행 격리 환경 같은 인프라는 처음 쓰는 단계에서 도입합니다. 큐 적재는 F2에서 붙입니다.

### F2. 큐 적재와 워커 소비 (FastAPI → 메시지 큐 → AI Worker)
- **목표**: 요청이 몰려도 큐에 쌓아 두고 워커가 하나씩 가져가 처리합니다(PLAN.md:8-11).
- **입력 → 출력**: F1의 작업 기록 → 큐 메시지 → 워커가 작업 상태를 전이(대기 → 처리 중 → 완료/실패)
- **포함 범위**
  - FastAPI 접수 경로에 큐 적재 연결
  - 워커 소비와 작업 상태 전이(같은 작업을 두 워커가 동시에 처리하지 않게)
  - 워커 장애 시 재전달, 반복 실패 작업 격리
- **완료 기준**: 요청 100건을 연속으로 보내도 FastAPI는 모두 즉시 202로 응답하고 워커가 전부 완료 상태로 만든다(PLAN.md:8). 처리 중 워커를 강제 종료해도 그 작업은 다시 처리된다.
- **임시 대체**: 워커 처리 내용은 "받은 작업을 완료로 표시"만 하고, F3에서 그래프로 바꿉니다.
- **먼저 정할 것**: OQ-08(큐 종류), OQ-09(동시성), OQ-19(배포 환경. 큐 선택지에 영향)

### F3. LangGraph 골격과 요청 분류 (경량 LLM)
- **목표**: 워커 안에서 LangGraph가 처리 순서를 관리하고, 첫 노드에서 요청을 경량 모델로 분류합니다(PLAN.md:16, 53).
- **입력 → 출력**: 큐에서 가져온 작업 → 분류 결과(요청 유형, 서비스·카테고리 같은 메타데이터) + 유형별 다음 경로 선택
- **포함 범위**
  - 그래프 뼈대: 상태, 체크포인트 저장, 재전달 시 이어 실행
  - 분류 노드: 경량 모델 호출, 구조화 출력, 외부 API 일시 오류 재시도
  - 역할 → 모델 매핑 설정, 노드별 토큰·비용 기록 시작
- **완료 기준**: 샘플 메시지 묶음의 분류 결과가 작업 기록에 저장되고 유형에 맞는 경로가 선택된다. 분류 뒤에 워커를 종료하고 재처리하면 분류를 다시 호출하지 않는다.
- **임시 대체**: 분류 뒤 노드는 "도달 기록만 남기는" 빈 노드로 두고 F4부터 채웁니다.
- **먼저 정할 것**: OQ-01(요청 유형과 분기), OQ-17(서비스·카테고리 체계), OQ-20(경량 모델), OQ-22(외부 LLM 데이터 반출 승인. 첫 LLM 호출 전에 필수), OQ-19(리전)

### F4. RAG 문서 검색 (임베딩 + Vector DB)
- **목표**: 사내 문서를 색인하고, 요청과 비슷한 문서를 메타데이터로 범위를 좁힌 뒤 찾습니다(PLAN.md:18, 53).
- **입력 → 출력**: (오프라인) 사내 문서 → 청크·벡터 / (요청 시) 요청 텍스트 + F3 메타데이터 → 관련 문서 top-k (질의응답형이면 근거를 인용한 답변까지)
- **포함 범위**
  - 문서 수집·청킹·임베딩·저장. 새 문서와 바뀐 부분만 다시 임베딩(PLAN.md:53)
  - 검색 노드: 질의 임베딩 → 메타데이터 선필터 → 유사도 검색
  - 질의응답형 경로의 답변 생성(OQ-01에서 질의응답을 포함할 때)
- **완료 기준**: 같은 문서 묶음을 두 번 색인하면 두 번째에는 임베딩 호출이 0건이다. 알려진 과거 장애를 묻는 질의에 그 장애 문서가 상위 결과에 포함된다.
- **먼저 정할 것**: OQ-16(문서 소스와 접근 권한), OQ-17(메타데이터 체계), OQ-18(Vector DB), OQ-20(답변 모델 등급)
- 가정: 문서 색인은 요청 흐름 밖(오프라인) 작업이지만, 빈 DB로는 검색을 검증할 수 없으므로 이 단계의 앞부분에서 먼저 만듭니다.

### F5. 원인 분석과 수정안 생성 (고성능 LLM)
- **목표**: 검색 문서와 대상 코드를 근거로 장애 원인을 분석하고 코드 수정안(패치)을 만듭니다(PLAN.md:30, 61).
- **입력 → 출력**: 요청 + 분류 + 검색 문서 + 코드 컨텍스트 → 원인 분석 + 패치(diff)
- **포함 범위**
  - 대상 저장소 접근과 코드 컨텍스트 확보
  - 원인 분석·패치 생성 노드(고성능 모델)
  - 패치 기본 검사: 기준 커밋에 적용되는지, 수정 금지 경로를 건드리지 않는지
- **완료 기준**: 원인을 알고 있는 샘플 장애에 대해 기준 커밋에 적용되는 패치가 작업 기록에 저장된다. 이 호출이 고성능 모델로 라우팅되고 토큰·비용이 기록된다.
- **먼저 정할 것**: OQ-02(대상 저장소와 접근 방식), OQ-03(언어·테스트 프레임워크), OQ-04(코드 컨텍스트 확보 방식), OQ-13(수정 금지 경로), OQ-20(고성능 모델, 분석·패치 분리 여부)
- 가정: F5~F8 검증에는 원인을 아는 장애와 테스트가 있는 샘플 대상 저장소가 필요합니다. 무엇으로 할지는 OQ-02/OQ-03 결정을 따릅니다.

### F6. diff·영향 범위 분석
- **목표**: 패치가 바꾼 함수와 그 함수를 쓰는 곳까지 영향 범위를 찾습니다(PLAN.md:43-46).
- **입력 → 출력**: 패치 + 대상 저장소 → 변경된 파일·함수 목록 → 영향받는 함수·모듈 목록
- **포함 범위**
  - diff 파싱과 변경 심볼 추출(어떤 파일·함수가 추가·수정·삭제됐는지, PLAN.md:43)
  - 호출·의존 관계를 거슬러 올라가 영향 범위 계산(PLAN.md:45-46)
- **완료 기준**: 샘플 저장소에서 로그인 쪽 함수를 바꾼 diff를 넣으면, 그 함수를 함께 쓰는 자동 로그인·토큰 갱신·SSO 경로까지 영향 범위에 나온다(PLAN.md:44 사례).
- **먼저 정할 것**: OQ-03(언어. 분석 방법이 언어마다 다름)

### F7. 테스트 선별과 실행
- **목표**: 영향 범위와 관련된 테스트만 골라 격리된 환경에서 돌립니다(PLAN.md:48, 64).
- **입력 → 출력**: 영향 범위 + 패치 → 선별 테스트 목록 → 테스트 결과(통과/실패, 실패 내용, 검증한 범위)
- **포함 범위**
  - 테스트와 코드의 대응 정보 준비, 영향 범위 기반 선별
  - 패치를 적용한 코드로 격리된 환경에서 실행(위치는 OQ-11), 결과 수집(실패 요약, 선별 수/전체 수)
- **완료 기준**: 정상 패치는 통과, 일부러 깨뜨린 패치는 실패로 판정된다. 영향 범위 밖 테스트는 실행되지 않고 선별 수/전체 수가 결과에 남는다.
- **먼저 정할 것**: OQ-11(실행 위치와 격리 수준), OQ-12(선별 0건일 때 정책, 대응 정보 갱신 주기), OQ-13(테스트 파일 수정 허용 여부)

### F8. 재수정 루프
- **목표**: 테스트가 실패하면 실패 내용을 AI에 돌려 수정안을 다시 만들고 다시 검증합니다(PLAN.md:50, 65).
- **입력 → 출력**: F7 실패 결과 + 시도 이력 → 실패 요약을 담아 F5로 복귀 / 상한에 도달하면 최종 실패
- **포함 범위**
  - 반복 조건: 시도 횟수 상한, 작업당 비용 상한
  - 실패 요약(긴 로그를 줄여 토큰 절감)과 시도 이력을 다음 생성 입력에 전달
- **완료 기준**: 첫 패치가 실패하도록 만든 샘플에서 실패 요약이 다음 생성 입력에 들어가고, 통과하면 승인 경로로 넘어간다. 계속 실패하면 상한에서 멈추고 최종 실패로 끝난다.
- **먼저 정할 것**: OQ-10(최대 시도 횟수, 시간 상한), OQ-21(비용 상한과 초과 시 동작), OQ-20(실패가 반복되면 상위 모델로 올릴지)

### F9. Slack 결과 회신과 승인 요청
- **목표**: 결과를 Slack으로 돌려주고, 검증을 통과한 수정안은 "여기까지 검증됐습니다"라는 근거와 함께 승인을 요청합니다(PLAN.md:1, 50).
- **입력 → 출력**: 작업 최종 상태(답변 / 검증 통과 수정안 / 최종 실패) → Slack 메시지 → (수정안이면) 승인 응답 → 작업 종료
- **포함 범위**
  - 결과 유형별 Slack 회신(질의응답 답변, 최종 실패 보고 포함)
  - 승인 요청 메시지: 원인, 변경 내용, 영향 범위, 실행한 테스트와 결과(PLAN.md:50)
  - 승인 응답 수신과 대기 중인 그래프 재개(응답자 확인, 중복 응답은 1회만 반영)
- **완료 기준**: 검증을 통과한 작업이 원 요청에 대한 결과와 승인 요청으로 Slack에 게시된다. 승인/거절 응답이 작업 기록에 한 번만 반영되고 작업이 종료 상태가 된다.
- **먼저 정할 것**: OQ-14(승인자, 승인 후 동작), OQ-15(회신 위치·형식), OQ-07(승인 응답을 받는 곳), OQ-25(응답 언어, 진행 알림)
- 가정: 승인 후 동작(PR 생성 등)은 OQ-14가 정해지면 F9에 넣되, 분량이 크면 상세 계획 단계에서 문서를 나눕니다.
